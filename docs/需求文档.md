# 需求文档

云购生活新零售企业——企业级数据仓库与经营分析可视化系统　　团队：ydsh-team　　姓名：张宇（20230308059）

## 一、业务背景

云购生活是一家新零售连锁企业，线下门店覆盖多省份，经营八个商品品类（数码、家居、美妆、食品、运动户外等），通过门店 POS、线上商城、小程序三渠道销售。随着业务扩张，企业面临三个核心经营问题：

1. **数据孤岛**：订单、用户、商品、门店数据分散在业务系统导出的 CSV 中，缺乏统一的数据仓库，无法跨主题关联分析；
2. **数据质量差**：源数据存在缺失、重复、枚举混乱、异常金额、格式不统一等五类脏数据，直接分析会得出错误结论；
3. **决策依赖人工**：经营指标靠 Excel 人工汇总，无自动化报表与可视化，缺乏智能问数能力。

为此启动"企业级数据仓库与经营分析可视化系统"建设项目，目标：构建 ODS→DWD→DWS→ADS 四层数仓，沉淀统一指标体系，配套 BI 仪表板、数据大屏与 NL2SQL 智能问数，支撑经营决策。

## 二、需求分析

### 2.1 业务需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| BR1 | 管理层需要随时掌握全期经营概况（销售额、订单量、客单价、复购率） | 高 |
| BR2 | 运营团队需要按月/按日监控销售趋势与环比变化，发现异常波动 | 高 |
| BR3 | 商品团队需要品类销售排行与占比，指导选品与库存 | 高 |
| BR4 | 门店管理团队需要门店/区域销售排行，评估门店绩效 | 中 |
| BR5 | 用户运营团队需要用户价值分层（高价值/潜力/一般/流失风险），支撑差异化营销 | 中 |
| BR6 | 管理层希望通过自然语言直接查询数据（智能问数），降低取数门槛 | 中 |
| BR7 | 系统需对未来一周销售额做预测，辅助备货与目标制定 | 中 |

### 2.2 数据需求

1. 数据范围：用户（1000）、商品、门店、订单（15600）、订单明细（37549）、用户行为共 6 类源表，合计约 11.5 万行；
2. 数据质量：接入时完成缺失值、重复行、枚举混乱、异常值、格式不统一五类脏数据的识别与修复；
3. 数据架构：按 Kimball 维度建模思想构建 ODS/DWD/DWS/ADS 四层；事实表按月分区、ORC 列存；
4. 数据一致性：各层行数与指标值须逐层吻合、可追溯（与《数据一致性核对清单》对照）。

## 三、指标体系定义（指标口径对照表）

所有指标统一从 ADS 层产出，口径定义如下：

| 指标 | 口径定义 | 产出表 | 实测值（2024 全年） |
|---|---|---|---|
| GMV（成交总额） | SUM(pay_amount)，订单状态=已完成 | ads_kpi_result | 14,151,214.68 元 |
| 订单量 | COUNT(DISTINCT order_id)，订单状态=已完成 | ads_kpi_result | 5,642 单 |
| 客单价 AOV | GMV / 订单量 | ads_kpi_result | 2,508.19 元 |
| 活跃用户数 | COUNT(DISTINCT user_id)（有完成订单） | ads_kpi_result | 997 人 |
| 复购率 | 下单≥2 次用户数 / 活跃用户数 | ads_kpi_result | 98.09%（人均 5.7 单，模拟数据特征） |
| GMV 日环比 | (当日 GMV − 前一日 GMV) / 前一日 GMV | ads_sales_daily | 逐日计算 |
| 品类销售排行 | 按品类 SUM(sales) 降序 Top10 | ads_category_top10 | 运动户外第一 |
| 用户价值分层 | 累计消费金额分档：≥2万 高价值 / 1.2万–2万 潜力 / 6千–1.2万 一般 / <6千 低价值 | ads_user_value | 201/379/309/108 人 |

口径说明：
1. 复购率 98.09% 显著高于真实零售场景（通常 20%~40%），源于模拟数据的人均订单量偏高（5.7 单/人），报告与分析中均须注明，避免误读为业务成果；
2. 金额类指标在清洗后计算（异常金额已按业务上限 10 万判定、P95 截断修复），保证口径一致；
3. 预测模型与 ADS 使用同一份清洗后明细（dwd_order），保证"预测口径 = 经营口径"。

## 五、约束与非功能需求

1. **性能**：常规 ADS 层查询应在 10 秒内返回（实测 Hive+Tez 均值 ~4.4s，满足）；
2. **安全**：NL2SQL 仅允许 SELECT，写操作（INSERT/UPDATE/DELETE/DROP）一律拦截；API 密钥通过 .env 注入，不入 Git 仓库；
3. **可复现**：全部脚本入库，`docker compose up -d` 一键启动；数据链路可通过 replay 脚本确定性重放（已在数据丢失事故中实测恢复，KPI 与丢失前完全一致）；
4. **合规**：可视化地图使用 ECharts 官方标准 china.js GeoJSON（含标准国界与南海诸岛）。
