## 三、高频问答预案

**Q1 GMV 口径是什么？为什么是 1415.12 万？**
已完成订单 pay_amount 求和；经 ODS→DWD→DWS→ADS 四层互验，DWD 明细 = DWS 日汇总 = ADS KPI = 14,151,214.68 元，一致才采信。

**Q2 脏数据怎么处理的？**
三类：15000 组重复订单去重（按 order_id）、负金额/超 10 万异常值截断到 P95（4833 元档）、渠道/状态字段归一化。详见数据质量清洗报告。

**Q3 去重规则会不会影响结果？**
诚实答法：原始数据有 198 组重复行时间相同、仅金额不同，我们已将去重规则升级为显式确定性排序（文件内出现顺序），保证任意环境重放结果可复现——这是第 5 周联调时发现并修复的可复现性问题。

**Q4 复购率 98.09% 怎么算的？**
有 ≥2 笔已完成订单的用户数 ÷ 活跃用户数（997 人），仿真数据购物频次高所致，口径见 ADS 层 ads_kpi_result。

**Q5 为什么分四层而不是直接建报表？**
ODS 保原始可回溯、DWD 明细标准化（清洗后单一事实源）、DWS 按天轻度汇总（复用）、ADS 面向应用（大屏/问答/Superset 共用同一套指标，改一处全端生效）。

**Q6 NL2SQL 怎么保证安全？**
生成 SQL 先过白名单校验：只允许 SELECT、禁 DML/DDL、强制 LIMIT 上限、只访问 ADS/DWD 白名单表，再交 Hive 执行。

**Q7 大屏数据为什么是静态的？**
演示数据集小、更新频率低，采用 ADS → data.js 导出方案换零延迟渲染与离线可用；实时化只需把导出改成定时任务/接口，架构预留了口子。

**Q8 Superset 遇到过什么问题？**
三个典型：新版移除 echarts_pie/dist_bar 插件（改用内置替代）、图表类型存在 params 与 slices.viz_type 双处存储（需 ORM 同步）、MySQL 驱动依赖 MySQLdb（pymysql 伪装）——都已解决并写入部署手册。

**Q9 容器重启数据会丢吗？**
Hive 数仓在命名卷 hive-warehouse、业务库在 mysql 卷；metastore 元数据已通过外部表 DDL 脚本固化，可一键重建（tmp_old/restore_meta.sql 思路已纳入部署手册）。

**Q10 压测为什么 QPS 只有 0.89？**
瓶颈在每次问答全链路走 LLM 生成 + Hive 执行，属教学演示规模；优化方向是 ADS 直连 + 结果缓存 + 连接池，已在反思日志中列为下一步。
