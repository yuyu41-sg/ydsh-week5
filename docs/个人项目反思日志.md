# 个人项目反思日志

云购生活新零售数仓项目（五周实训）　　张宇（20230308059）　　ydsh-team　　2026-11-23

## 一、技术维度

**掌握最扎实的**
1. 四层数仓建模：从 Kimball 星型模型的表设计到分区/分桶的实操取舍（按天分区 366 分区回滚失败 → 改按月 12 分区一次成功），这条踩坑链比教科书深刻；
2. 数据清洗工程化：五类脏数据的处理不是"写几个 CASE WHEN"，而是预评估 → 策略选择（P99 被极值污染改用业务上限+P95 截断）→ 修复率验证 → 守恒校验的闭环；
3. Docker 数据持久化：经历"force-recreate 清空数仓 → 全链路脚本重放恢复 → KPI 分毫不差"的事故后，真正理解了有状态数据必须上命名卷、以及"可重放性"是数据工程的生命线。

**仍需加强的**
1. 预测建模：特征工程停留在滞后/滑窗基线层面，时序模型（ARIMA/Prophet/LSTM）只在报告里做了对比性认知，未实际落地；
2. 性能调优：只会看分区裁剪与 JOIN 优化，对 Tez 执行计划、数据倾斜处理的理解还停留在现象层；
3. 前端与可视化定制：ECharts 大屏是配置驱动的组合，缺乏对前端工程（组件封装、状态管理）的深入实践。

## 二、协作维度

1. **Git 协同的真实感**：亲手制造 README 冲突、在 GitHub 上看 "Can't automatically merge"、用融合策略（两侧措辞都保留）解决并留痕——比背十遍 rebase 教程都有用；
2. **每周独立仓库的教训**：week1 曾混入 week2 内容被迫两次迁移提交，体会到"边界清晰"在多人协作里的价值；
3. **文档即协作**：五大文档统一口径（尤其指标口径对照表）后发现，此前散落各周报告的数字第一次能互相印证——文档不是交差，是团队对齐的接口。

## 三、表达维度

1. **10 分钟讲清一个系统**：先业务价值、再技术亮点、最后工程化的顺序，比按周流水账更有效；
2. **诚实是表达的一部分**：预测退化、AI 幻觉、压测瓶颈这些"不好看"的结果如实呈现，反而成了答辩最有说服力的部分；
3. **写文档逼着想清楚**：架构设计文档里"为什么选星型模型""为什么不用 P99"，写之前只是模糊的直觉，写完才真正立得住。
