## 一、总体架构

系统采用「数仓四层 + 分析 AI + 可视化 + 容器化部署」的整体架构，数据自下而上逐层加工，职责逐层收敛：

```
业务系统 CSV 数据源
      │  LOAD DATA 原样接入
      ▼
┌─────────────────────────────────────────────┐
│ ODS 贴源层  ydsh_ods（6 表，TEXTFILE）        │  保留原始脏数据
├─────────────────────────────────────────────┤
│ 清洗加工：缺失值/去重/枚举标准化/异常值/        │
│           格式统一/字段合并/编码映射            │
├─────────────────────────────────────────────┤
│ DWD 明细层  ydsh_dwd（事实+维度，ORC，星型）   │  清洗后明细
├─────────────────────────────────────────────┤
│ DWS 汇总层  ydsh_dws（4 表，按月分区）         │  主题轻度汇总
├─────────────────────────────────────────────┤
│ ADS 应用层  ydsh_ads（5 表）                  │  经营指标
└─────────────────────────────────────────────┘
      │                    │                 │
      ▼                    ▼                 ▼
 预测模型/BI 洞察       NL2SQL 智能问数    Superset 仪表板
 （线性回归/LLM）      （智谱 GLM）        ECharts 数据大屏
                           │
                           ▼
                 Docker Compose 一键部署
        （MySQL / metastore / hive-server / superset / app）
```

## 二、数仓四层设计

### 2.1 分层职责与命名规范

| 层 | 库名 | 表数 | 存储格式 | 职责 |
|---|---|---|---|---|
| ODS 贴源层 | ydsh_ods | 6 | TEXTFILE | 最细粒度保留原始脏数据，不做任何清洗 |
| DWD 明细层 | ydsh_dwd | 事实 3 + 维度 6 | ORC | 清洗后明细事实 + 星型维度表 |
| DWS 汇总层 | ydsh_dws | 4 | ORC 按月分区 | 按日/维度粒度轻度汇总 |
| ADS 应用层 | ydsh_ads | 5 | ORC | 面向报表/大屏的最终指标 |

通用规范：库名 `ydsh_<层>`；字段小写下划线；日期 `xxx_date`、时间戳 `xxx_timestamp`、金额 `xxx_amount`；事实表一律按日期分区。

### 2.2 DWD 星型模型

**事实表**（度量 + 外键）：
- dwd_order：订单事实表，度量 = pay_amount / discount_amount；外键 = user_id / store_id / order_date；**按 order_month 分区（12 个月）+ user_id 分 4 桶**；
- dwd_order_item：订单明细事实表；
- dwd_user_behavior：用户行为事实表。

**维度表**（描述属性 + 主键）：
- dim_user / dim_product / dim_store / dim_date：核心维度；
- dim_member_level / dim_pay_type：编码映射维度（第 2 周清洗配套新建）。

**选型理由**：星型模型维度表非规范化、事实表外键直连维度，JOIN 路径短、查询简单，符合 Kimball 维度建模推荐，适合销售分析场景。

### 2.3 分区与分桶策略（含踩坑）

- **分区**：dwd_order 按 order_month 分月分区，实测 12 分区一次成功；按天分区方案失败——Hive 动态分区默认上限 100，调参后 366 分区一次性提交仍触发 metastore MoveTask 回滚。**结论：中等数据量按月分区是可靠性与裁剪收益的平衡点**；
- **分桶**：dwd_order 按 user_id 分 4 桶（CLUSTERED BY ... INTO 4 BUCKETS），为用户级 JOIN 与抽样优化预留；
- **分区裁剪实测**：带分区条件的查询仅读 1/12 数据量，耗时 4.9s→4.4s；小数据集下固定开销（建连+Tez DAG 提交）占主导，亿级数据下裁剪收益是数量级级别的。

### 2.4 DWS 汇总层（第 3 周）

| 表 | 粒度 | 说明 |
|---|---|---|
| dws_order_day | 日 × 全局 | 366 行，日 GMV/订单量 |
| dws_order_store_day | 日 × 门店 | 门店维度汇总 |
| dws_order_category_day | 日 × 品类 | 品类维度汇总 |
| dws_order_channel_day | 日 × 渠道 | 渠道维度汇总 |

## 三、AI 与分析模块架构

### 3.1 销售预测（python/predict_gmv.py）

- 特征：滞后 1/7 天 GMV、7 日滑动均值、星期几（dow）；模型：线性回归；
- 评估：最后 30 天滚动测试，MAPE 31.7%，与均值基线（31.5%）几乎持平——**诚实结论：本模拟数据日销为随机波动、无可学习信号，模型退化为均值外推**；该边界分析作为"批判性审视 AI 局限"的素材保留。

### 3.2 NL2SQL 智能问数（python/nl2sql.py）

三道防线保证可靠：
1. **生成约束**：schema（10 表结构+注释+few-shot）注入系统提示词，限定 SELECT；
2. **安全拦截**：正则检测 INSERT/UPDATE/DELETE/DROP/ALTER 等写关键字，命中即拒绝执行；
3. **报错自修复**：Hive 执行报错后把错误信息回传大模型重写 SQL（最多 2 次重试）。实测修复案例：GLM 生成 `GROUP BY 别名` 触发 Hive 10004 方言错误，1 次重试即收敛。

### 3.3 AI 经营洞察（python/ai_insight.py）

自动完成异常归因与经营摘要，并配**人工验证机制**：实测 AI 归因引用的数字存在幻觉（订单量 443→448 上升被说成 469→448 下降），报告以"人工验证实录"呈现核查过程，体现 AI 协同的批判性使用。

## 五、部署架构（Docker Compose）

| 服务 | 镜像 | 端口 | 依赖 |
|---|---|---|---|
| ydsh-mysql | mysql:8.0 | 3306(宿 3307) | — |
| ydsh-metastore | apache/hive:4.0.0 | 9083 | mysql (healthcheck) |
| ydsh-hiveserver2 | apache/hive:4.0.0 | 10000 | metastore；warehouse 目录挂命名卷持久化 |
| superset | apache/superset:6.1.0 | 8088 | 接入 ydsh 网络访问 Hive/MySQL |
| app | 自建（Streamlit） | 8501 | hive-server |

要点：
1. healthcheck + depends_on 保证启动顺序（mysql → metastore → hive-server）；
2. **warehouse 命名卷持久化**：容器可写层易失（曾因 force-recreate 丢数据，靠全链路脚本重放恢复且 KPI 分毫不差），加固后重建容器数据不丢；
3. 密钥经 .env 注入（.gitignore 排除），绝不入库入仓。

## 六、技术选型汇总

| 类别 | 选型 | 理由 |
|---|---|---|
| 数据存储与计算 | Hive 4.0 + Tez | 企业级数仓标准栈，SQL 化开发成本低 |
| 元数据/业务库 | MySQL 8.0 | metastore 后端 + ADS 结果镜像库 |
| 建模方法论 | Kimball 星型模型 | 面向分析的维度建模事实标准 |
| 数据清洗 | Hive SQL（全脚本化） | 可重放、可审查、可版本管理 |
| 预测建模 | Python + pandas + sklearn | 轻量、可解释、基线对比严谨 |
| LLM | 智谱 GLM glm-4-flash | OpenAI 兼容接口、免费额度、中文能力强 |
| BI | Superset | 开源、多数据源、图表丰富 |
| 大屏 | ECharts | 地图/热力等图表类型完备 |
| 部署 | Docker Compose | 一键编排、教学环境轻量 |
